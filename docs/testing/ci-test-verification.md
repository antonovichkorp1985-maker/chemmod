# Как CI доказывает, что тесты действительно выполнялись

Ссылка на «CI зелёный» сама по себе не доказывает, что конкретный набор тестов
запускался. Этот документ фиксирует, что именно проверяется автоматически, и
почему добавлен явный контроль результатов тестов.

## Порядок проверок в `scripts/smoke-test.sh`

1. `python3 -m unittest discover -s scripts -p 'test_*.py'` — контракт ресурсов
   лаборатории, метаданные релиза и инструменты проверки сборки.
2. `./gradlew check installDist :mod:build` — компиляция `core`/`core-cli`/`mod`,
   JUnit-тесты обоих модулей и сборка дистрибутивного мода.
3. `python3 scripts/junit_summary.py` — проверка XML-отчётов JUnit (ниже).
4. Проверки CLI: поиск этанола, изометрическая идентичность, баланс горения,
   data-defined реакция, состав и лицензия собранного JAR.
5. `scripts/server-smoke-test.sh standalone` и `create` — headless-сервер без
   Create и с Create.
6. `./gradlew :mod:runGameTestServer` — игровые GameTest-проверки.

`.github/workflows/ci.yml` выполняет этот скрипт, затем публикует JUnit-сводку,
считает SHA-256 JAR и выкладывает артефакт ручной приёмки. Отдельный workflow
`release` срабатывает только на точный коммит релиза и не участвует в ветке
разработки.

## Почему результаты тестов проверяются отдельным шагом

Gradle-задача `check` в корневом проекте запускает `check` во всех подпроектах,
поэтому `:core:test` обычно выполняется вместе со сборкой. Но это соглашение
графа задач, а не проверяемый факт: переименование задачи, отключённый модуль или
ошибка конфигурации могут оставить сборку зелёной без выполнения тестов.

`scripts/junit_summary.py` читает `*/build/test-results/test/*.xml` и завершает
работу ненулевым кодом, если:

- отчётов нет вообще;
- отсутствуют результаты модуля `core` (`io.github.antonovichkorp.chemmod.core`);
- в любом классе есть `failures` или `errors`;
- отчёт не удалось разобрать.

При успехе печатаются строки вида
`core core.thermal.ThermalTransferTest: tests=16 failures=0 errors=0 skipped=0`
и итог `JUnit totals: classes=… tests=… failures=… errors=… skipped=…`.

Логика разбора отчётов покрыта `scripts/test_junit_summary.py` на синтетических
XML-файлах во временном каталоге: подсчёт по модулям, отказ при ошибках, отказ
при отсутствии отчётов и при отсутствии `core`, неразбираемый XML, обёртка
`<testsuites>` и отсутствующие атрибуты.

## Читаемость результатов без сырых логов

Сырые логи GitHub Actions не всегда доступны для загрузки, из-за чего причину
падения приходилось восстанавливать по обрезанным аннотациям. Поэтому шаг
«Publish JUnit summary annotation» (`if: always()`) дополнительно публикует ту же
сводку одной аннотацией `JUnit summary`, доступной через Checks API, независимо
от состояния сборки.

Ограничения, которые этот механизм **не** закрывает:

- он не проверяет содержимое тестов, только факт выполнения и заявленные счётчики;
- GameTest-результаты приходят из `:mod:runGameTestServer`, а не из JUnit XML,
  поэтому в сводку не входят;
- зелёный CI не заменяет ручную приёмку M3 и не доказывает поведение в реальном
  клиенте, перезапуске мира или мультиплеере.
